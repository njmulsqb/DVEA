What Can XSS Do in Electron?

The same injection, three configurations, three very different blast radii.

Guide: What is happening?

In a browser, cross-site scripting is contained by the browser's own sandbox — the worst a payload can usually do is act within that one page's origin. Electron runs web code with a bridge to Node.js and the operating system, so the exact same XSS payload can range from harmless in-page mischief to full remote code execution on the host. Which one you get is determined entirely by the app's webPreferences configuration — not by anything different in the injected payload itself.

Objective: Show, hands-on, that "how bad is this XSS" is a property of an Electron app's configuration, not of the injected payload — the same unsanitized innerHTML injection is walled off in one window and becomes RCE in another.

Why config is the story

Electron security comes down to a small set of switches: sandbox, contextIsolation, nodeIntegration, and what the preload script chooses to expose through contextBridge. Set correctly, XSS stays trapped in the renderer no matter how the attacker got their script onto the page. Set incorrectly, the boundary between attacker-controlled JavaScript and the operating system disappears.

The three challenges below are the identical bug — unsanitized input rendered via innerHTML — placed at three different points on that spectrum. Nothing about the injection changes between them; only the webPreferences around it does.

The switches, in detail
  • sandbox — when true, the renderer process runs inside Chromium's OS-level sandbox and cannot touch Node.js or the filesystem directly, regardless of what else is misconfigured.
  • contextIsolation — when true, the preload script's JavaScript world is isolated from the page's own world; the page can reach only whatever the preload deliberately exposes via contextBridge.exposeInMainWorld.
  • nodeIntegration — when false (the safe default), require() and Node globals are not reachable from page script at all.
  • What the preload exposes — even with the three flags above all set correctly, a preload that hands the page a privileged function (one that shells out, reads arbitrary files, etc.) reopens the door XSS was supposed to be locked out of. Correct core config plus one careless API is enough to undo it.

Challenge 1 — Contained: hardened config; XSS is walled to the renderer Challenge 2 — Bridged: correct isolation, one overprivileged preload API Challenge 3 — Owned: main process evaluates renderer input with full Node access

How the challenges work

Each challenge sets out concrete tasks. Solving one proves a capability that its configuration allows — reading page data, reaching a privileged API, executing a shell command — and returns a flag in the form DVEA{...}.

Watch the config badges at the top of each challenge page and the Config Inspector panel while you work — the difference in what's achievable from challenge to challenge is the configuration difference, not a different vulnerability. Pay attention to failures as much as successes: a wall you hit in Challenge 1 trying to reach the filesystem is one you'll sail straight through in Challenge 3 with the exact same attempted action.

Real-world grounding

This escalation is not contrived. CVE-2020-16608 is exactly XSS escalating to RCE via Node access in a misconfigured Electron app — the same shape as Challenge 3. The Electron security checklist exists specifically to keep real apps out of Challenge 2 and Challenge 3 territory.
