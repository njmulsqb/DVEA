openExternal Abuse MOD.03

shell API · Protocol Handling · Medium · cf. CVE-2020-25019

Unvalidated URLs passed to shell.openExternal() trigger arbitrary OS protocol handlers

01 Guide what is happening

Deep links are the inbound half of Electron's protocol-handling trust surface — an external, attacker-craftable link drives the app. shell.openExternal() is the outbound mirror: instead of the app receiving a URL, the app hands one out to the operating system, and the OS launches whatever handler is registered for that URL's scheme — a browser for https:, a mail client for mailto:, or any other app that has claimed a custom scheme. Both directions are the same underlying failure — trusting a URL's scheme/host to decide what gets launched, on either side of the process boundary.

The form below sends whatever URL you enter straight to the main process, which calls shell.openExternal(url) without any validation or allowlist. Electron does not restrict which schemes reach the OS this way — https:, mailto:, tel:, slack://, vscode://, file://, and any other OS-registered or app-installed custom scheme are all handed off identically, with no inspection.

Objective: This app is written as if shell.openExternal() only ever opens ordinary web links. Your job: prove it will launch far more than that — get it to hand OS-level protocol handlers attacker-chosen input. The challenge isn't "type a URL and click the button" — a plain https: link proves nothing. It's to escape the "web links only" assumption entirely.

How to try it: The input starts empty on purpose. Whatever string you type is handed to shell.openExternal() exactly as given, with no inspection — and every attempt you make is reported below the form, showing the scheme that actually got launched and, where it's a recognizable one, what kind of handler that scheme maps to. Use that feedback loop: start with something ordinary, then start reasoning about what other kinds of URLs exist, what schemes are registered as protocol handlers on a typical machine, and watch the result panel confirm the app hands each one off exactly the same way, with zero discrimination between them.

Real-world instance: CVE-2020-25019 (Jitsi Meet Electron) showed how unsafely passing user-controllable URLs to shell.openExternal led to code execution. Positive Security's "1-click RCE in Electron" research documents the same unsafe pattern across many apps (Telegram, Nextcloud, VLC, Wireshark, Mumble, Bitcoin wallets).

How this is exploited in the real world (why typing it yourself still matters)

In a real attack, the victim never types the malicious URL — this lab's input field is a stand-in for attacker-controlled input that reaches shell.openExternal() through some other weakness elsewhere in the app. This lab isolates one specific flaw: an unvalidated scheme lets the OS launch whatever handler it's registered to. The mechanisms below are how attacker input actually reaches that flaw in production apps — none of them require the victim to type anything.

  • XSS reaching an openExternal bridge. A cross-site-scripting bug in a renderer that has access to an openExternal-backed API lets injected script call it directly with an attacker URL, with zero user input. This is literally CVE-2020-25019 (Jitsi Meet Electron), and the same pattern is documented across many apps in Positive Security's "1-click RCE in Electron" research.
  • Rendered untrusted content. The app displays attacker-controlled content — a chat message, an email body, a shared post — and routes a link the victim clicks (or one embedded/auto-opened from that content) through shell.openExternal() without checking its scheme first. The victim clicks something that looks like an ordinary link; the app is the one that decided what to hand to the OS.
  • Deep link forwarding. A custom-scheme handler receives a URL parameter from an external myapp://... link — something the attacker crafted and got the victim to click, not something the victim typed — and forwards it straight into shell.openExternal(), chaining one protocol-handling flaw into another. (Deep links themselves are the subject of the separate Deep Link Hijacking module.)

The real danger isn't https: or mailto: — it's custom protocol handlers registered by other apps already installed on the machine (slack://, vscode://, zoommtg://, and hundreds more). Invoking one of those with attacker-controlled arguments, via a vulnerable shell.openExternal call exactly like this one, is what led to code execution in CVE-2020-25019. Every custom scheme is a potential pivot into whatever that other app does with the input it receives — and DVEA's handler doesn't care which one you pick.

Discover what's actually registered on your own machine. On Linux, registered schemes are declared in .desktop files as x-scheme-handler/<scheme> MIME associations — the same enumeration technique used in the Deep Link Hijacking module, just pointed at every app on the system instead of one:

# list every custom scheme any installed app has registered, and which app owns it
1
grep -rn "x-scheme-handler/" /usr/share/applications/ ~/.local/share/applications/

(macOS: check each app bundle's Info.plist for CFBundleURLSchemes; Windows: HKEY_CLASSES_ROOT entries with a URL Protocol value.) Pick a scheme that turns up, work out what a URL for it looks like, and try launching it through this lab.

02 Impact
!! impact An attacker can make the app launch arbitrary URLs or OS protocol handlers on the victim's machine, potentially triggering phishing pages, malware downloads, or OS-level protocol-handler exploits. Custom protocol handlers registered by other installed apps can be invoked with attacker-chosen arguments, pivoting the attack into whatever that handler does with its input.
