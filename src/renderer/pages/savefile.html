Insecure File Write (IPC Abuse)

An IPC handler trusts a renderer-supplied path — and hands the renderer the host filesystem

✓ NodeIntegration: false ✓ ContextIsolation: true ✓ Sandbox: true ✗ IPC: writes a renderer-supplied path, no validation

Guide: What is happening?

In a browser, page JavaScript cannot touch the filesystem — there is no API that lets a script open an arbitrary path and write bytes to it. That's a deliberate, load-bearing part of the web sandbox. Electron reopens exactly that door, on purpose, through IPC: the renderer asks the main process to do something, and the main process runs with the full privileges of the OS user the app launched as.

The moment an IPC handler writes to a path the renderer chose, all of the renderer hardening above stops mattering. sandbox, contextIsolation, and nodeIntegration: false keep the renderer from calling fs itself — but they do nothing about a main-process handler that takes a renderer-supplied path and writes it anyway. The renderer never needed require('fs'); it just needed to ask a handler that already has it.

The danger isn't "overwrite a text file." Arbitrary file write is a general-purpose primitive: change what the app loads on next launch, drop a file into a location the OS or another program will execute, replace a config file that decides how software behaves, or establish persistence. A renderer compromised by XSS — or one that renders attacker-controlled content — can reach this handler and weaponize it, without the victim doing anything.

Objective: This app is written as if its "Save File" feature only ever drops a harmless note into its own saves folder. Prove that assumption is a fiction. The challenge isn't "type a path and click Save" — it's to demonstrate that the write is not confined anywhere, that it can replace files the app already owns, and finally that it can rewrite a file the app itself reads — turning "save a file" into control over what the app does. Craft the paths and content yourself; nothing is pre-filled.
This genuinely writes to your real filesystem with this app's permissions — there is no simulation layer. The flags below only ever check DVEA-controlled files under a temporary directory, so the challenge is safe to run repeatedly, but the handler itself will write wherever you point it. Don't aim it at anything you care about.

Tasks

  • Unsolved Task 1 — Write outside the intended directory. The app claims its writes only ever land in its own saves folder. Write a file somewhere that has nothing to do with DVEA at all, proving there is no path restriction.

  • Unsolved Task 2 — Overwrite an existing file. DVEA already planted a file it owns (see recon). Replace its contents — proving write can clobber an existing file, not just create a new one.

  • Unsolved Task 3 — Weaponize: change what the app does (the capstone). Overwrite the config file the app reads (see recon) so the banner above changes to content you chose — turning "write a file" into control over the app's own behavior.
