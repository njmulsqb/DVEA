Deep Link Hijacking

unvalidated dvea:// deep links let external attacker-crafted links drive the trusted app window

Guide: What is happening?

Browser vs Electron: In a browser an open redirect is lower severity because the address bar shows the destination. In an Electron app there is no address bar, so a trusted app window can be driven to attacker content with no visible signal.

Deep links are an unauthenticated external entry point into the installed desktop app. The OS routes a dvea:// link (from email, chat, or a webpage) directly into the running application process.

Objective: Load attacker-controlled content in the trusted app window with no visible signal to the user.

The vulnerability: the main process parses the deep link and directly navigates the app window to the attacker-supplied URL with no allowlist or validation.

Deep link format:

dvea://navigate?url=<attacker>
Impact: An attacker who convinces a user to click a crafted dvea:// link can make the trusted app window display attacker content (e.g., a phishing page) without any address-bar signal — enabling credential harvests.

Note on the deep link / OS registration

The dvea:// scheme must be registered with the OS for deep links to open the app. Packaged installs register this reliably; when running from source (e.g., npm start) on Linux the scheme is typically not registered, so clicking a dvea:// link will fall through to the system default. In development, use the route demos' "Simulate Deep Link" button — they exercise the same vulnerable navigation code path as a real deep link. To demo real dvea:// links, install a packaged build so the OS routes the scheme to DVEA.
