Deep Link Hijacking

unvalidated dvea:// deep links let external attacker-crafted links drive the trusted app window

Guide: What is happening?

Browser vs Electron: In a browser an open redirect is lower severity because the address bar shows the destination. In an Electron app there is no address bar, so a trusted app window can be driven to attacker content with no visible signal.

A deep link is a custom URI scheme — like dvea:// — that the operating system associates with a specific desktop application. When registered, the OS routes any link using that scheme to the app, launching it if necessary and handing it the full URL.

In Electron, an app claims a scheme by calling app.setAsDefaultProtocolClient('dvea'). Once registered with the OS, clicking a dvea:// link anywhere — a browser, an email, a chat message, a webpage — wakes the app and delivers the link to it. The app receives the URL through platform events (open-url on macOS, second-instance / process arguments on Windows and Linux) and decides what to do with it.

The critical property: the link comes from outside the application, and anyone can craft one. The app is being driven by input it did not generate and cannot trust.

Objective: Load attacker-controlled content in the trusted app window with no visible signal to the user.

The vulnerability: the main process parses the deep link and directly navigates the app window to the attacker-supplied URL with no allowlist or validation.

Deep link format:

dvea://navigate?url=<attacker>
Impact: An attacker who convinces a user to click a crafted dvea:// link can make the trusted app window display attacker content (e.g., a phishing page) without any address-bar signal — enabling credential harvests.

What deep links are normally used for

Deep links are a legitimate, widely-used feature. Common examples:

  • "Open in app" — a website offers slack://channel/... or vscode://file/... to hand off from the browser to the desktop app.
  • Password reset / magic links — an email link opens the app directly to a specific flow.
  • OAuth / SSO callbacks — the auth provider redirects to myapp://auth?code=... to return control to the desktop app.
  • Inter-app workflows — one app launches another with context via its scheme.

The pattern is convenient precisely because it lets external content reach into the app — which is also exactly why it is dangerous when the app trusts that content.

Common mistakes developers make

The deep-link handler is, in effect, an unauthenticated remote API into the desktop app: any link the user can be convinced to click invokes it. Developers routinely forget this and make mistakes such as:

  • Trusting the URL's contents. Passing a redirect/url parameter straight to loadURL() with no allowlist — letting an attacker load arbitrary content in the trusted window (see Deep Link → Untrusted Navigation).
  • Trusting path parameters. Handing a path parameter to the filesystem with no validation — enabling path traversal and arbitrary file access (see Deep Link → Path Traversal).
  • Routing deep links to privileged actions. Wiring myapp://settings?... or myapp://run?... to state-changing or sensitive operations, so a single crafted link can invoke capabilities the developer assumed only the user could reach.
  • Treating the link as authenticated. Assuming that because the app opened the link, the user intended the action — when in reality an attacker authored the link.
  • Forgetting the missing UI signal. In a browser the address bar warns the user where they are; an Electron window has no address bar, so the user has no way to tell the trusted app is now showing or doing something attacker-controlled.

How to fix them

  • Treat every part of a deep link as fully untrusted input — the same posture you'd take toward a request from the public internet.
  • Validate and allowlist. For navigation, allowlist origins before loadURL(). For file paths, canonicalize and confirm the resolved path stays within an intended directory. Reject anything that doesn't match.
  • Never route deep links to privileged actions without explicit user confirmation. A link should not be able to silently change settings, move funds, or run code.
  • Re-authenticate / re-confirm for anything sensitive rather than assuming the link implies user intent.
  • Keep the handler minimal — the fewer capabilities reachable via the scheme, the smaller the attack surface.

Enumeration — finding an app's deep-link attack surface

To attack (or audit) deep links, you first have to discover which schemes an app registers and what its handler does with them. There are three vantage points; a thorough researcher checks all of them.

1. OS-level registration — no source required

The operating system records which app owns which scheme, so you can enumerate an app's schemes without ever reading its code. This works on any installed app — including DVEA once it's installed as a .deb.

Linux — registered schemes are declared in .desktop files as x-scheme-handler/<scheme> MIME associations: 

# What app is registered to handle dvea:// ?
xdg-mime query default x-scheme-handler/dvea

# Find every app that registers ANY custom scheme
grep -rl "x-scheme-handler/" /usr/share/applications/ ~/.local/share/applications/

# Inspect a specific app's desktop entry for its schemes and launch command
cat /usr/share/applications/dvea.desktop

macOS — schemes are declared in the app bundle's Info.plist under CFBundleURLTypes → CFBundleURLSchemes: 

plutil -p /Applications/DVEA.app/Contents/Info.plist | grep -A5 CFBundleURLSchemes

Windows — registered schemes live in the registry, each with a URL Protocol value and a shell "open" command: 

HKEY_CLASSES_ROOT\dvea   (look for the "URL Protocol" value and shell\open\command)

This vantage point tells you the scheme(s) an app claims — but not the routes/actions behind the handler. For that, go to the source.

2. Source analysis — the deepest view

With the app's source (extraction methods covered separately), search for how the scheme is registered and, more importantly, how the handler parses the URL and dispatches to routes. This reveals the deep-link "API" — every action reachable through the scheme. 

# Scheme registration
grep -rn "setAsDefaultProtocolClient" .
grep -rn "protocol.handle\|registerFileProtocol\|registerHttpProtocol" .

# Where deep links arrive
grep -rn "open-url\|second-instance\|will-finish-launching" .

# The scheme string and its routes
grep -rn "dvea://" .

Trace from the arrival event into the handler: how it parses the URL, which query parameters it reads, and which routes/actions it dispatches to (e.g. navigate, open). That mapping is the attack surface — each route is a candidate for abuse.

3. Manifest & runtime — supporting angles

  • Build manifest — schemes are often declared in the build config. With the source tree, check package.json and the electron-builder/electron-forge config (e.g. build.protocols) for declared schemes in one place.
  • Runtime observation — feed the app a link and watch what it does: process launches and command-line arguments (strace/ps on Linux, Process Monitor on Windows). This shows the handler's actual behavior, useful when source is obfuscated.
  • Route probing — once the scheme is known, unknown routes can be discovered by trying plausible action names and observing responses, ideally confirmed against the source.
The takeaway: You can map a deep-link attack surface from three directions: the OS tells you which schemes exist (no code needed), the source reveals the scheme and every route behind the handler, and runtime confirms what actually happens when a link fires. On DVEA, start at the OS level against the installed .deb — enumerate the dvea:// scheme from its .desktop entry — then use source analysis to map its routes (navigate, open) and attack them via the routes below.

Note on the deep link / OS registration

The dvea:// scheme must be registered with the OS for deep links to open the app. Packaged installs register this reliably; when running from source (e.g., npm start) on Linux the scheme is typically not registered, so clicking a dvea:// link will fall through to the system default. In development, use the route demos' "Simulate Deep Link" button — they exercise the same vulnerable navigation code path as a real deep link. To demo real dvea:// links, install a packaged build so the OS routes the scheme to DVEA.
